01

The brief

SSoT는 함께 쓰는 판단 기준입니다

SSoT(Single Source of Truth)는 업무에 필요한 사실을 판단하고 갱신할 때 사용하는 정본입니다. AXS 관점에서는 기준 데이터에 업무 의미, 실행 권한, 검증 기록을 연결합니다.

같은 데이터를 보는 데서 나아가,
같은 기준으로 판단하고 상태를 바꾸도록 만듭니다.

When to use

Agent를 업무에 붙이기 전

  • 팀마다 서로 다른 문서를 기준으로 판단할 때
  • 데이터는 있지만 AI가 맡을 실행이 불분명할 때
  • 인사·재무·총무·기획 업무를 실행 단위로 나눌 때
  • 팀장과 실무자에게 공통 기준을 설명할 때

What to prepare

시작에 필요한 여섯 가지

  • 업무명
  • 기대 결과
  • 현재 사용하는 문서·표·시스템
  • 업무 상태 변화
  • 승인·검증이 필요한 지점
  • Agent가 맡을 실행 단위

결과를 정하고, 필요한 기준만 만듭니다

데이터를 모두 모은 뒤 활용할 일을 찾으면, 데이터 구조가 실제 업무와 떨어질 수 있습니다. Backward Implementation은 Agent에게 맡길 결과에서 출발합니다.

The three layers

기준값 · 의미 · 실행 권한

1.

Data Foundation

신뢰 가능한 기준값

무엇을 기준으로 판단할까?

기준 시스템·문서·원장을 정하고, 소유자·기준일·최신성·변경 이력을 명시합니다. 시스템끼리 값이 다를 때의 우선순위도 필요합니다.

예: 지급 원장 / 인사 규정 / 예산 코드
2.

Context Layer

데이터의 업무 의미

이 값으로 무엇을 판단할까?

필드가 설명하는 Entity, 판단할 State, 입력으로 쓰이는 Transition을 연결합니다. 예외와 위험을 함께 기록합니다.

예: 사용률 저하의 의미 / 적용 규정의 예외
3.

Access Layer

접근과 실행 통제

Agent는 어디까지 할 수 있을까?

읽기, 초안, 승인 후 쓰기, 차단을 구분합니다. Human Gate와 접근 금지 데이터, 로그·감사 위치를 정합니다.

예: 보고 초안은 가능 / 예산 변경은 검토 필요

Pilot 01 / HR

HR 문의 답변 초안

기준값을 확인한 답변 초안과 처리 상태 기록을 만듭니다.

후보 예시

Entity · HR 문의

접수됨→규정 확인됨→초안 생성됨→HR 검토 대기→답변 완료→기록 완료
조건부 분기 제안 · 정보가 부족하면 보완 요청 후 규정 확인으로 돌아갑니다. 반려·예외 문의는 검토자에게 전달하고, 승인되지 않은 답변을 완료로 처리하지 않습니다.

기준값과 맥락

  • 인사 규정, 조직도, 승인권자 목록, FAQ·처리 사례
  • 문의 유형, 적용 규정, 예외 조건, 민감정보 여부
  • 읽기 범위는 허용된 문의와 규정으로 제한

Agent와 사람의 역할

  • Agent: 자료 읽기, 답변 초안·체크리스트 작성
  • 사람: 최종 답변 검토, 예외 승인, 인사 조치
  • 검증 제안: 규정 버전·승인 로그·최종 답변·처리 원장 대조
첫 실행 단위 설계안 · “규정 확인됨 → 답변 초안 생성됨”
입력 / SignalActionGuard / Gate완료 증거
필수 문의 정보와 적용 규정 확인 기록근거 규정과 예외를 표시한 답변 초안 생성규정 충돌·민감 사안은 HR 검토로 전달. 최종 발송은 사람 검토 대상초안 링크, 참조 규정 버전, 문의 ID와 상태 read-back

그 외 원문 후보: 신규 입사·조직 변경 정보 정리, 회의록 action item 추출, 직무·역량·평가 문서 초안화.

Pilot 02 / Finance

비용·사용량 이상치 요약

기준값과 비교해 이상치와 의사결정 포인트를 요약합니다.

후보 예시

Entity · 비용 항목 / 라이선스 / 예산 코드

조건부 분기 제안 · 이상치가 있으면 근거와 질문을 표시하고, 없으면 “이상치 없음”과 점검 범위를 기록합니다. 기준 불일치·누락은 보완 후 다시 비교합니다.

기준값과 맥락

  • 예산 원장, 비용 집행 기준, 라이선스 계약, 사용량
  • 비용 증감, 일회성·반복 비용, 고가치 사용·낭비
  • 예산 cap과 의사결정 기준

Agent와 사람의 역할

  • Agent: 허용된 자료 읽기, 요약·이상치·질문 작성
  • 사람: 예산 변경, 지급·회수, 계약 변경 승인
  • 검증 제안: 비용 합계·집계 기간·계약 기준·보고 반영본 대조
첫 실행 단위 설계안 · “기준값 확인됨 → 검토용 요약 생성됨”
입력 / SignalActionGuard / Gate완료 증거
같은 기간의 예산·사용량·계약 기준증감·이상치와 추가 확인 질문 작성예산·계약 자동 변경은 차단. 확정 보고는 담당자 검토합계 대조 결과, 근거 링크, 검토 로그, 최종 보고 링크

그 외 원문 후보: 예산·비용 요약, AI 도구 TCO·효익 비교, 비용 증감 보고 초안, 팀별 사용량·예산 소진 현황. 추가 Entity 후보: 비용 집행 요청 / 사용량 리포트 / ROI 가설.

PoC 범위 제안1개 팀 → 1개 업무 → 1개 Entity → 1개 Transition. 어떤 전이를 먼저 맡길지는 보고에서 결정할 항목으로 남아 있습니다.

Human gate & verification

승인, 실행, 검증을 각각 정의합니다

원문 Playbook은 인사·평가, 개인정보, 비용·예산, 계약, 외부 시스템 쓰기, SSoT 기준 변경, 최종 보고·배포를 사람 승인 대상으로 제시합니다. 다음 표는 원문의 권한 예시를 모은 것입니다.

02 · SSoT 가이드 1-page · AXS TFssot-guide-1page-axs-tf.md

2026-09-22 SSoT 가이드 1-page - AXS TF

목적: KEP 비개발자 AI Native 적응 과정에서 팀장/실무자가 SSoT를 어떻게 이해하고 만들지 설명하기 위한 1-page 가이드
연결 개념: AXS TF, Native AI Engine, Backward Implementation, Data Readiness
핵심 메시지: SSoT는 데이터베이스가 아니라 사람과 AI가 같은 기준으로 판단하게 만드는 업무 기준값이다.

1. SSoT란 무엇인가

SSoT(Single Source of Truth)는 업무에 필요한 사실을 판단하고 갱신할 때 사용하는 정본이다.

AXS 관점에서 SSoT는 단순한 저장소가 아니다.

SSoT는 AI에게 정보를 주기 위한 참고자료가 아니라, 사람과 AI가 같은 기준으로 판단하게 만드는 업무 기준값이다.

예:

업무SSoT 예시
AI 도구 지급계정 지급 원장, 조직/팀 목록, 예산 cap, 라이선스 정책
인사 Agent인사 규정, 조직도, 직무/역할 정의, 승인권자
재무 Agent예산 코드, 비용 집행 기준, 라이선스 계약, 사용량 데이터
회의/보고회의록, 결정사항 로그, action item 원장, 최종 보고 문서

2. SSoT를 먼저 크게 만들지 않는다

나쁜 접근:

데이터를 다 모은다
→ 온톨로지를 만든다
→ AI가 뭘 할지 찾는다

AXS 방식:

Agent에게 맡기고 싶은 결과를 정한다
→ 필요한 Entity / State / Transition을 정의한다
→ 그 전이를 판단하는 데 필요한 SSoT만 만든다

즉 SSoT는 Backward Implementation으로 만든다.

Desired Result
→ Entity
→ State
→ Signal
→ Transition
→ Constraint / Guard
→ 필요한 SSoT / Data

3. SSoT는 3개 층으로 준비한다

Agentic AI를 위한 SSoT는 다음 세 층으로 본다.

1) Data Foundation — 신뢰 가능한 기준값
  • 정답지 역할을 하는 문서/시스템/원장
  • 최신성, 소유자, 변경 이력, 기준일이 명확해야 함
2) Context Layer — 업무 의미
  • 이 데이터가 어떤 Entity를 설명하는가?
  • 어떤 State를 의미하는가?
  • 어떤 Transition의 입력인가?
  • 어떤 예외/위험이 있는가?
3) Access Layer — Agent 접근/실행 통제
  • Agent가 무엇을 읽을 수 있는가?
  • 무엇을 draft할 수 있는가?
  • 무엇은 Human Gate가 필요한가?
  • 무엇은 절대 자동 실행하면 안 되는가?

0. 핵심 정의

SSoT는 단순히 데이터를 한 곳에 모아놓은 저장소가 아니다.

SSoT는 사람과 AI가 같은 기준으로 판단하고, 같은 업무 세계에서 상태 전이를 수행하게 만드는 기준값이다.

따라서 SSoT 생성은 다음을 만드는 일이다.

신뢰 가능한 기준값
+ 업무 의미
+ Agent 접근/실행 통제
+ 검증 가능한 기록

1. 왜 SSoT가 필요한가

비개발자 AI Native 적응에서 가장 위험한 상황은 다음이다.

사람마다 다른 문서를 본다.
팀마다 다른 기준으로 판단한다.
AI에게 다른 context를 넣는다.
Agent마다 다른 세계를 갖는다.
결과는 빠르게 나오지만 기준이 다르다.

이렇게 되면 AI 도구를 많이 써도 조직 생산성은 올라가지 않는다.

SSoT가 필요한 이유는 다음이다.

  1. 사람과 AI가 같은 기준으로 판단하게 한다.
  2. Agent가 현재 업무 상태를 알 수 있게 한다.
  3. 상태 전이가 가능한지 판단하게 한다.
  4. 위험한 전이를 Human Gate에 걸 수 있게 한다.
  5. 실행 결과를 다시 읽어 검증할 수 있게 한다.
  6. 반복된 업무를 Playbook/Skill로 남길 수 있게 한다.

2. SSoT 생성의 나쁜 순서와 좋은 순서

나쁜 순서: Data-first
데이터를 모은다
→ 온톨로지를 만든다
→ AI가 뭘 할 수 있을지 찾는다

문제:

  • 데이터는 많지만 실행할 업무가 불분명하다.
  • 온톨로지는 정교하지만 현업 업무 표면과 연결되지 않는다.
  • Agent가 어떤 상태 전이를 맡아야 하는지 알 수 없다.
좋은 순서: Execution-first / Backward Implementation
어떤 결과를 만들고 싶은가?
→ 어떤 Entity가 있는가?
→ 어떤 State를 거치는가?
→ 어떤 Signal로 상태 변화를 아는가?
→ 어떤 Transition이 필요한가?
→ 어떤 Guard가 필요한가?
→ 그제야 어떤 SSoT/Data가 필요한가?

이 순서가 AXS TF의 SSoT 생성 방식이다.

3. SSoT의 3계층

3.1 Data Foundation — 신뢰 가능한 기준값

Data Foundation은 업무의 정답지다.

질문:

  • 이 업무에서 최종 기준으로 삼을 문서/시스템/원장은 무엇인가?
  • 최신 정보인가?
  • 누가 소유자인가?
  • 변경 이력이 남는가?
  • 서로 다른 시스템이 다르게 말할 때 무엇을 우선할 것인가?

예:

업무Data Foundation
AI 도구 지급지급 원장, 조직도, 예산 cap, 라이선스 정책
인사 문의인사 규정, 조직도, 승인권자 목록
재무 비용예산 코드, 비용 집행 기준, 계약/라이선스 정보
회의 브리핑회의록, 결정사항 로그, action item 원장

3.2 Context Layer — 업무 의미

Context Layer는 데이터의 업무 의미를 설명한다.

질문:

  • 이 데이터는 어떤 Entity를 설명하는가?
  • 이 필드는 어떤 State를 판단하는 데 쓰이는가?
  • 값이 높거나 낮다는 것이 업무적으로 무슨 의미인가?
  • 어떤 예외 조건이 있는가?
  • 어떤 Transition의 입력인가?

예:

tool_usage_rate = 12%

이 숫자만 보면 의미가 부족하다.

Context Layer는 이렇게 설명한다.

사용량이 낮음은 미사용, 업무 부적합, 교육 부족, 접근 문제, 또는 아직 PoC 전 단계일 수 있다.
따라서 바로 회수하지 않고 팀장 인터뷰 또는 사용 장애 확인 Transition으로 보낸다.

3.3 Access Layer — Agent 접근/실행 통제

Access Layer는 Agent가 데이터를 어떻게 사용할 수 있는지 정한다.

질문:

  • Agent가 읽을 수 있는 데이터는 무엇인가?
  • 초안을 만들 수 있는 데이터는 무엇인가?
  • 시스템에 write할 수 있는가?
  • 어떤 경우 Human Gate가 필요한가?
  • 어떤 데이터는 절대 Agent가 접근하면 안 되는가?
  • 로그와 감사 기록은 어디에 남기는가?

권한 예시:

Agent 행동권한Guard
회의록 읽기read민감정보 redaction
보고 초안 작성draft지정 검토자 확인
action item 원장 업데이트write with approval담당자 확인
비용/예산 변경blocked / draft only재무 승인 필요
인사 평가 반영blockedHR 책임자 승인 필요

질문:

  • 보고 문서

질문:

예:

Step 4. Signal / Observation 정의

질문:

상태가 바뀌었다는 것을 무엇으로 알 수 있는가?

예:

  • 새 요청서 생성

  • 예산 초과 표시
  • 회의록 결정사항

Step 5. Transition 정의

질문:

상태를 바꾸기 위해 어떤 실행이 필요한가?

예:

  • 기준값 조회
  • 승인 요청
  • 초안 생성
  • 담당자 배정
  • 계정 지급
  • 원장 업데이트
  • 보고서 반영

Step 6. Constraint / Guard 정의

질문:

어떤 전이는 막거나 사람 승인이 필요한가?

예:

  • 예산 cap 초과
  • 개인정보 포함
  • 인사/평가 관련
  • 외부 시스템 write

0. 보고 목적

이번 보고의 목적은 KEP 비개발자 AI Native 적응을 교육/툴 지급 중심이 아니라, 실제 업무 표면에서 AI를 호출하고 검증하는 AXS TF 운영 모델로 정렬하는 것이다.

보고에서는 아래 3가지를 확인/공유한다.

  1. 툴 지급 논의 현황 문의
  2. SSoT 관련 가이드 공유
  3. 인사/재무 Agent PoC 공유

1. 보고 아젠다

1) 툴 지급 논의 현황 문의

확인할 질문:

  • 현재 AI 도구 지급 논의는 어디까지 진행되었는가?
  • 비개발직군 대상 지급 범위/시점/예산 cap은 어떻게 잡히고 있는가?
  • 팀 단위 지급인지, 개인 단위 지급인지, AI Champion 중심 지급인지?
  • Claude Code / Codex / Gemini / Grok 등 기반 도구의 지급 원칙은 어떻게 정리되는가?
  • 사용량 모니터링은 평가가 아니라 운영/지원 목적으로 설명되고 있는가?
  • Shadow AI / 개인 결제 도구 사용은 어떻게 제도권으로 흡수할 것인가?

보고 메시지:

툴 지급은 출발점일 뿐이고, 실제 성과는 팀 업무 표면에서 AI가 어떤 상태 전이를 수행하게 되는지에 달려 있습니다.
2) SSoT 관련 가이드 공유

공유할 핵심 관점:

SSoT는 AI에게 정보를 주기 위한 참고자료가 아니라, 사람과 AI가 같은 기준으로 판단하게 만드는 업무 기준값입니다.

공유할 구조:

Desired Result
→ Entity
→ State
→ Signal
→ Transition
→ Constraint / Guard
→ 필요한 SSoT / Data

SSoT 가이드에 포함할 내용:

  • 업무별 기준 시스템/문서 지정
  • Entity 정의
  • 필수 데이터 필드
  • 상태 판단 기준
  • 변경 이력 관리
  • 승인/검증 규칙
  • AI가 읽을 수 있는 문서/표 구조
  • Human Gate 위치

보고 메시지:

SSoT를 먼저 크게 만들기보다, Agent에게 맡기고 싶은 업무 결과에서 뒤로 거슬러 올라가 필요한 SSoT만 최소 정의하는 방식이 필요합니다.
3) 인사/재무 Agent PoC 공유

PoC의 목적:

  • 인사/재무 업무에서 AI Agent가 실제 업무 표면에서 호출될 수 있는지 확인
  • 교육이 아니라 실업무 루프 안에서 AI가 어떤 Transition을 맡을 수 있는지 검증
  • Native AI Engine 방식의 가능성 확인

PoC 후보 업무:

인사 Agent PoC

예시 업무:

  • 신규 입사/조직 변경 관련 정보 정리
  • 제도/규정 질의 응답 초안
  • 회의록 기반 action item 추출
  • 직무/역량/평가 관련 문서 초안화

Entity 예시:

입사자 / 조직변경 요청 / HR 문의 / 평가 문서 / 회의록

State 예시:

요청됨 → 정보 부족 → 기준값 확인됨 → 초안 생성됨 → 사람 검토 대기 → 승인됨 → 기록 완료
재무 Agent PoC

예시 업무:

  • 예산/비용 데이터 요약
  • AI 도구 TCO/효익 비교
  • 비용 증감 보고 초안
  • 팀별 사용량/예산 소진 현황 정리

Entity 예시:

예산 항목 / 비용 집행 요청 / 툴 라이선스 / 사용량 리포트 / ROI 가설

State 예시:

데이터 수집됨 → 기준값 확인됨 → 이상치 표시됨 → 요약 생성됨 → 검토 대기 → 보고 반영됨

보고 메시지:

인사/재무 Agent PoC는 Agent를 먼저 만드는 실험이 아니라, 인사/재무 업무의 Entity-State-Transition 세계를 정의하고 그 일부 전이에 Agent를 배치하는 실험입니다.

2. 보고용 한 장 메시지

핵심 주장
KEP 비개발자 AI Native 적응은 AI 교육이나 도구 지급만으로는 완성되지 않습니다.
실제 업무 표면에서 AI를 호출할 수 있는 SSoT, 업무 Entity, State, Transition, Human Gate를 정의하고, 그 위에 Agent를 배치해야 합니다.
AXS TF 정의
AXS TF는 AI를 쓰게 만드는 조직이 아니라, AI가 일할 수 있는 업무 세계를 만드는 조직입니다.
보고에서 얻고 싶은 결정/피드백
  • 툴 지급 논의의 현재 상태와 의사결정 일정
  • SSoT 가이드를 팀장님들에게 공유해도 되는지
  • 인사/재무 Agent PoC를 어떤 업무부터 시작할지
  • PoC 범위: 1개 팀 / 1개 업무 / 1개 Entity / 1개 Transition으로 시작할지

3. Backward Implementation으로 본 보고 구조

Desired Result:
보스가 AXS TF의 다음 실행 방향을 이해하고, 툴 지급/SSoT/PoC에 대한 피드백을 준다.

Entity:
보고 아젠다 / SSoT 가이드 / 인사 Agent PoC / 재무 Agent PoC

State:
준비됨 → 보고됨 → 피드백 수집됨 → PoC 후보 확정 → 실행 계획화

Signal:
보고 일정, 보스 피드백, 툴 지급 현황 답변, PoC 승인 여부

Transition:
자료 공유, 질문, 피드백 기록, PoC 후보 선정, 다음 액션 정리

Guard:
인사/재무 민감정보, 평가/비용 관련 결정, 외부 시스템 write는 Human Gate 필요
